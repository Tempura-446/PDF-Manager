# Security Features and Protecting ZPDF: Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** two things.
1. **Security for the people using ZPDF:** stronger protection of their documents, and safer handling of documents they didn't make.
2. **Protection for ZPDF itself:** the owner's rights to the code, and the guarantee that what friends install is exactly what the owner published.

## Already in place

- **The local server:** a token on every request, only `localhost` Host headers accepted, and a strict Content-Security-Policy on the app page (`gui.py`). The 0.16 security review was applied.
- **Documents:** AES-256 encryption with permission flags; certificate signing and signature checks (pyHanko); true redaction that removes the content; Sanitize (scripts, actions, metadata, attachments); a hostile-PDF robustness suite; and the 0.27 sweep with a weekly CI run.
- **Updates:** the Update button installs a zip only if its SHA-256 matches the published checksum (`update.py`).
- **The repository:** public, PolyForm Internal Use licence plus personal use, `main` protected by a ruleset (pull requests, required checks, no force pushes).

## Part 1: security features for users

### Phase 1 (release A): safer opening of documents you didn't make

**Done in 0.39.0** (`risks.py`, the `makesafe` tool, `reader.js` `_openLink`; `tests/test_risks.py`, `tests/test_risks_ui.py`).

- [x] **Risk check on open.** The file panel shows a chip (with the details on hover) for scripts, launch actions, attachments that can run, forms that submit, a web address opened by itself, links that hide their target, and pointers at other files. **Make safe** takes out everything but the misleading links and keeps the rest, including a form's own totals and formats.
- [x] **Links.** Clicking an external link asks first and shows the real address; the More menu (and the dialog) turn the asking off. Only http, https, mailto and tel are opened.
- [x] **Embedded files.** Saving ones that could run warns. ZPDF never opens them itself.
- [x] **Tests:** PDFs with each kind of risk; each is reported, and Make safe removes it while keeping pages, text and forms.
- [x] Found by the Windows checks and fixed in 0.39.0: the reader's form-script sandbox ran a PDF's own scripts (now only the named form functions with plain values, by the same pattern as the check); WebView2 offered one PDF's form entries in another's fields (autocomplete off).
- [ ] Seen in the checks, to look at: every reader tab's accessible name ends in ", unsaved" though only edited tabs show the dot; `pdfm make-safe --check` exits 0 when it finds risks.
- [ ] Left for later: the details as a list in the panel instead of a hover; a "require Make safe on open" setting (Phase 8's policies); XFA forms are not reported.

### Phase 2 (release B): stronger protection of documents

Split in two. **B1 is done in 0.40.0** (`protection.py`, `redact.check_redacted`; `tests/test_protection.py`, `tests/test_protection_ui.py`); B2 is next.

**B1 (0.40.0)**
- [x] **Password strength:** a meter under "Password to open" (Very weak to Strong, with a reason), worked out locally; the command line warns too.
- [x] **Old encryption:** `protection.info` names a file's encryption without its password; RC4 files get a "weak protection" chip and a "Protect it better" suggestion; **Upgrade protection** (`pdfm upgrade-protection`) re-encrypts with AES-256, keeping the password and the limits (both passwords when the permissions password is given: the password to open is worked out from it, as the old scheme allows).
- [x] **Redaction proof:** after Black out the written file is searched for the redacted words and patterns in the page text, details, bookmarks, form values, comments, attachments (names and contents) and the rest of the file's data, for text left under the boxes, and for earlier versions kept in the file. The result is one sentence in the tool's notes and on the command line.
- [x] **Tests:** each of the above, including a word hidden in the title and in an attachment, and a file with an earlier version inside.

**B2 (done in 0.41.0, except long-term validation)** (`certcrypt.py`; `tests/test_certcrypt.py`, `tests/test_certcrypt_ui.py`)
- [x] **Encrypt for people, not with a password:** `certcrypt.encrypt_for` (pyHanko's public-key security handler, AES-256) for certificates given as .cer/.crt/.pem/.der or a Digital ID; `certcrypt.open_with_id` writes an unprotected copy. Tools "Encrypt for people" and "Open with Digital ID", `pdfm encrypt-for` / `open-with-id`. The reader shows such a file as protected for people (not damaged) and opens it with a Digital ID into a new tab; every other tool names what the file is.
- [x] **Signatures over time:** the trusted timestamp (RFC 3161) was already an option when signing; Check signatures now says, for each signature, whether it stays checkable after the signer's certificate expires (timestamped) or until when (not).
- [ ] **Long-term validation (PAdES-B-LT):** embedding the certificate chain and revocation data when signing. It needs the issuing authority's servers to be reachable at signing time and a certificate from a real authority to test with; left for Phase 6, which is about the PAdES levels.
- [ ] Left for later: listing who a file is protected for without opening it; per-person permissions; a default recipient list (address book of certificates); the redaction check as a saved report.

### Phase 3 (release C): privacy of your own machine

- [x] **Temporary files (0.42.0):** `privacy.begin_run` points the app's working files at one folder per running copy (`temp/run-<pid>` in the data folder, private to the user); it's deleted when the app closes and folders of copies no longer running are swept at start-up. The command line keeps the system's temporary folder (each command cleans up after itself).
- [x] **Recent files and caches (0.42.0):** Settings → Privacy: "Clear history" removes the Recent list, file facts, the search text (`search.sqlite`) and the reader's remembered positions; "Remember the files I open" off keeps none of them. `pdfm privacy`.
- [x] **No telemetry, stated (0.42.0):** `privacy.ONLINE`, shown in Settings → Privacy → When ZPDF goes online; a test fails when another module starts opening connections.
- [x] **Tests:** `tests/test_privacy.py`, `tests/test_privacy_ui.py` + `tests/privacyui.js`.
- [ ] Left for later: overwriting working files before deleting them (best effort only on SSDs); the WebView2 profile's own cache; clearing measurements and scales as a separate, explicit choice; the log (it names no files, so it's kept).
- [ ] Seen in the 0.41.0 checks, to look at: a tool result opened in the reader shows no unsaved dot; refusals on the reader's card are small grey text and the dialog closes after one; the palette doesn't find Open with Digital ID for "certificate"; the certificate box shows only "2 files"; Check signatures' card doesn't print the "Later on:" label; Acrobat hasn't been tried on a file protected for people.

## Part 2: protecting ZPDF itself

**The honest limit:** the source is public on GitHub, and the release zip contains ZPDF's source, which the installer installs. Anyone can read it. Hiding Python or JavaScript code that ships as source isn't possible, and obfuscation only slows a determined reader down. What can be protected is the owner's **rights** and the **integrity** of what people install.

### Phase 4 (release D): rights

- [ ] **A copyright line in every source file** (`# Copyright (c) 2026 Tempura-446. Licensed under the PolyForm Internal Use License 1.0.0 with a personal-use permission; see LICENSE.`), plus a short header in the JavaScript, HTML and CSS. Add a test that fails if a new file lacks it.
- [ ] **The name and logo:** a `TRADEMARKS.md` saying the ZPDF name and icon may not be used for other software or modified copies. A trademark is protected by use; registering it is optional and costs money, so it's the owner's decision.
- [ ] **Copies on GitHub:** a short note in the README on reporting copies that break the licence (GitHub's DMCA process), and a `SECURITY.md` for reporting vulnerabilities privately.
- [ ] **Decision for the owner:** keep the repository public, or make it private again. Private hides the source on GitHub, but the release zip still contains it, and CI would go back to a limited allowance of minutes or the self-hosted runner. One middle way: keep the repository private and publish only built apps (the PyInstaller build) instead of the source zip. The installer would then install the built app. That hides plain source from casual readers, though the bundled Python can still be extracted.

### Phase 5 (release E): integrity of what friends install

- [ ] **Signed releases:** sign each release zip and its checksum with a key only the owner holds. A minisign or OpenSSH signature costs nothing; the public key is built into ZPDF. The Update button then refuses a zip whose signature doesn't verify, not just one whose checksum doesn't match, so a tampered release on GitHub can't install itself. `release.py` signs; the key lives on the owner's PC, never in the repository.
- [ ] **Code-signing the app (owner's decision, costs money):**
  - Authenticode-sign the launcher and the installer, through Azure Trusted Signing (about US$10 a month) or a code-signing certificate (about US$100–400 a year).
  - It removes the "Windows protected your PC" SmartScreen warning and proves the files came from the owner.
  - It works without it, but the warning stays.
- [ ] **Supply chain:**
  - pin dependency versions with hashes for the installer (`requirements.txt` with `--require-hashes`), so a hijacked package version can't be installed;
  - `pip-audit` in CI, weekly, for known vulnerabilities in dependencies;
  - GitHub's Dependabot alerts and secret scanning (free for public repositories);
  - CodeQL code scanning for Python and JavaScript.
- [ ] **The account:** two-factor authentication on the GitHub account, plus signed commits on `main`. The ruleset can require them once the owner's PC signs commits.
- [ ] **Tests:**
  - an update with a bad signature is refused;
  - a release made by `release.py` verifies with the built-in key;
  - the installer refuses a dependency whose hash doesn't match.

## Part 3: enterprise-level security protocols

What Acrobat Pro and Enterprise, Foxit PDF Editor and Nitro offer organisations, measured against ZPDF. Each item says which standard it follows. The out-of-scope list at the end says what isn't taken on, and why.

### Phase 6 (release F): signatures to the European and Adobe standards

- [ ] **PAdES baseline levels** (ETSI EN 319 142): B-B (basic), B-T (with a trusted timestamp), B-LT (with validation data) and B-LTA (with archive timestamps that renew long-term proof). Choose the level when signing. pyHanko implements all four.
- [ ] **Certifying signatures (DocMDP):** the author certifies the document and chooses what others may still do: nothing; fill forms and sign; or also comment. ZPDF's tools then respect those permissions and warn before breaking them.
- [ ] **Signature fields that lock fields (FieldMDP)** when signed, and seed values (the required reason, certificate issuer or level), for forms with several signers in order.
- [ ] **Sign with any certificate Windows has:**
  - the Windows certificate store, through CNG/CAPI, so company smart cards and USB tokens work when their driver puts the certificate in the store;
  - PKCS#11 tokens directly, with the user choosing the token's library.

  No key ever leaves the card.
- [ ] **Trust and validation:**
  - validate against the Windows trusted roots, plus optional trust lists: the EU Trusted Lists (eIDAS, public) and Adobe's AATL (if its terms allow a local copy);
  - check revocation online by OCSP or CRL when the user allows it, else with the embedded validation data;
  - a validation report exportable as PDF, and as ETSI-style XML for auditors.
- [ ] **Detached signatures (CAdES/CMS `.p7s`)** of any file, and their verification.
- [ ] **Tests:**
  - B-LTA validates offline years later (with a mocked clock);
  - a certified "no changes" document refuses edits with a clear message;
  - a FieldMDP-locked field can't be changed after signing;
  - a signature from a test smart card works (SoftHSM PKCS#11 in CI).

### Phase 7 (release G): security policies, watermarks, audit

- [ ] **Security profiles:** named, saved sets applied in one step and usable in recipes and watch folders. For example, "Confidential" could mean: AES-256, no printing or copying, encrypted for the team's certificates, a CONFIDENTIAL watermark, metadata removed, Make safe applied. Export and import them as files, so a team shares the same profiles.
- [ ] **Dynamic watermark on print:** printing stamps the user's name, date and time and "Printed copy" (configurable), so leaked paper copies can be traced. Optionally the same on export.
- [ ] **Redaction for regulated work:**
  - redaction reason codes shown on each box (FOIA exemptions such as (b)(6), or GDPR Art. 17, with custom sets);
  - pattern sets for national ID formats (US SSN and EIN, UK NI number, EU IBAN, credit cards with a Luhn check);
  - a redaction log (what, where, why, who and when), exportable;
  - "Remove hidden information" as one step: metadata, earlier versions, comments, hidden layers, form data, attachments, search index and bookmarks pointing at removed text.
- [ ] **Audit log:** a local, append-only log of security actions (encrypt, decrypt, sign, certify, redact, Make safe, profile applied, password removed). Each entry is chained to the previous one by a hash, so tampering shows. View, filter and export it in Settings.
- [ ] **Tests:**
  - a profile applied through a watch folder produces exactly its settings;
  - the print watermark appears on printed output (to PDF);
  - the log detects an edited entry;
  - a redaction log lists every box with its reason.

### Phase 8 (release H): managed deployment and hardening

- [ ] **Administrator settings (policies):** settings read from `HKLM\Software\Policies\ZPDF` (and the per-user `HKCU` equivalent) take precedence and are shown as locked in Settings. Examples:
  - turn off all internet use (updates, timestamps, packs, web printing);
  - require Make safe on open;
  - force a security profile on save;
  - turn off removing passwords;
  - set the trust lists;
  - turn off the Update button (updates managed by IT).

  Provide an ADMX/ADML template so Group Policy and Intune can set them.
- [ ] **Enterprise install:**
  - an MSI package (per-machine or per-user, silent install and uninstall switches, an upgrade code for clean upgrades), built in CI alongside the zip;
  - code-signed (this needs the Part 2 signing decision);
  - an offline update channel: point the Update button at a company file share instead of GitHub.
- [ ] **Processing isolation:**
  - every tool job runs in a child process with memory and time limits (the sweep harness already does this), at low integrity on Windows where possible;
  - pdf.js keeps rendering inside WebView2's sandbox;
  - PDF JavaScript is never executed (already true).

  A crashing or hostile file can then never take the app down or reach the user's files beyond the job's.
- [ ] **FIPS mode (optional):** an administrator policy that limits crypto to FIPS 140-validated algorithms (AES-256, SHA-256 and up, RSA ≥ 2048, ECDSA P-256 and up) and refuses RC4, MD5 and SHA-1 for new files. True FIPS validation needs the OpenSSL FIPS provider configured under `cryptography`; document that as the organisation's step.
- [ ] **Tests:**
  - a policy in a mocked registry locks its setting and changes behaviour;
  - the MSI builds, and installs and uninstalls silently on the Windows CI runner;
  - a job that allocates too much is stopped and reported;
  - FIPS mode refuses RC4 encryption.

### Not taken on (and why)

- **Microsoft Purview / AIP sensitivity labels and rights management:** reading or applying labelled, rights-protected PDFs needs Microsoft's MIP SDK (licensed, Windows and online, organisation accounts). Possible later as an optional add-on if the owner ever needs it.
- **Adobe Experience Manager or LiveCycle rights-management servers, SSO and identity integration, SIEM forwarding, MDM-specific features:** these need servers and accounts, which don't fit an offline personal app. The audit log export and policies above cover the local part.
- **Common Criteria or FIPS validation certificates for ZPDF itself:** formal certification costs tens of thousands of dollars per version. ZPDF can follow the same algorithms and practices, but can't claim certification.

## Order and size

| Release | Phase | Size | Notes |
|---|---|---|---|
| A | 1: risk check on open, Make safe, safer links and attachments | medium | protects users the most, soonest |
| B | 2: certificate encryption, password strength, timestamp/LTV signatures, redaction proof | medium–large | |
| C | 3: temporary files, Clear history, no-telemetry list | small | |
| D | 4: copyright headers, trademark note, SECURITY.md, the public/private decision | small | mostly documents |
| E | 5: signed releases and updates, supply-chain checks, account hardening, optional code signing | medium | some steps need the owner (keys, 2FA, money) |
| F | 6: PAdES B-B to B-LTA, certifying and field-locking signatures, smart cards and Windows store, trust lists, validation reports, CAdES | large | builds on B's timestamps and LTV |
| G | 7: security profiles, print watermark, regulated redaction (reason codes, ID patterns, log), audit log | medium | |
| H | 8: administrator policies (ADMX), MSI install, offline updates, job isolation, FIPS mode | large | MSI and code signing go together |

**Place in the roadmap (Part 3):** F after B, then G, then H, which is mostly useful once ZPDF is used in an organisation.

**Place in the roadmap:** D and the free parts of E (signed releases, `pip-audit`, Dependabot, secret scanning) are small and worth doing soon, right after 0.30. A comes next. B and C fit alongside the drawing tools, paragraph reflow and language packs.

**Decisions for the owner:**
- the repository public or private, and whether to publish built apps instead of the source zip;
- whether to pay for code signing;
- whether to register the ZPDF trademark;
- turning on 2FA and signed commits on the GitHub account.
