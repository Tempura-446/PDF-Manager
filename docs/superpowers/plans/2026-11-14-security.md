# Security Features and Protecting ZPDF: Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** two things.
1. **Security for the people using ZPDF:** stronger protection of their documents, and safer handling of documents they didn't make.
2. **Protection for ZPDF itself:** the owner's rights to the code, and the guarantee that what friends install is exactly what the owner published.

## Already in place

- **The local server:** a token on every request, only `localhost` Host headers accepted, and a strict Content-Security-Policy on the app page (`gui.py`). The 0.16 security review was applied.
- **Documents:** AES-256 encryption with permission flags; certificate signing and signature checks (pyHanko); true redaction that removes the content; Sanitize (scripts, actions, metadata, attachments); a hostile-PDF robustness suite; and the 0.27 sweep with a weekly CI run.
- **Updates:** the Update button installs a zip only if its SHA-256 matches the published checksum (`update.py`).
- **The repository:** public, PolyForm Internal Use licence plus personal use, `main` protected by a ruleset (pull requests, required checks, no force pushes).

## Part 1: security features for users

### Phase 1 (release A): safer opening of documents you didn't make

- [ ] **Risk check on open.** The file panel shows what a PDF can do:
  - JavaScript, launch or URI actions;
  - embedded files, especially executables and Office files with macros;
  - links that hide their target (display text ≠ URL);
  - forms that submit to the internet;
  - external references (GoTo remote, import data).

  Use plain words and a severity, for example "This PDF can run scripts. ZPDF never runs them." Add a **Make safe** button: Sanitize with the dangerous parts removed and everything else kept.
- [ ] **Links.** Clicking an external link asks first and shows the real address. Settings can turn the asking off.
- [ ] **Embedded files.** Saving one that could run (exe, js, vbs, docm and similar) warns first. ZPDF never opens them itself.
- [ ] **Tests:** PDFs with each kind of risk; each is reported, and Make safe removes it while keeping pages, text and forms.

### Phase 2 (release B): stronger protection of documents

- [ ] **Encrypt for people, not with a password:** certificate-based (public-key) encryption. Only the holders of the chosen certificates can open the file. Use pyHanko or pypdf's public-key security handler (Adobe.PubSec), with the user's own digital ID from the existing Sign setup. Also decrypt with your own ID.
- [ ] **Password strength:** a strength meter when setting a password, and a warning about the old, weak RC4/40-bit encryption when opening such files, with **Upgrade to AES-256**.
- [ ] **Signatures that stay valid:**
  - a trusted timestamp (RFC 3161, a free public TSA, chosen in Settings; online only when signing);
  - long-term validation (embedded certificate chain and revocation data: PAdES-B-LT);
  - re-checking a signed file shows "still valid in 10 years" or "will expire".

  pyHanko supports all of these. This was already on the idea list as stronger certificate signatures.
- [ ] **Redaction proof:** after Black out, a check report lists every removed item and confirms that none of the redacted words appear anywhere in the file (text, metadata, bookmarks, form values, attachments, earlier revisions).
- [ ] **Tests:** the certificate-encrypted file opens with the right ID and not with another; a timestamped and LTV signature validates offline; the redaction proof catches a word hidden in an earlier revision.

### Phase 3 (release C): privacy of your own machine

- [ ] **Temporary files:** jobs' working files live in one per-run folder under the app's data folder. They're deleted when the job ends and swept at start-up in case of a crash. Optionally, they're overwritten before deletion (best effort; SSDs can't promise it).
- [ ] **Recent files and caches:** "Clear history" in Settings removes the Recent list, the search cache (`search.sqlite`), file facts, thumbnails and the reader's remembered positions. "Don't remember files" turns all of this off.
- [ ] **No telemetry, stated.** ZPDF goes online only to check for updates (with a switch), download language packs on request, fetch a timestamp when signing with one, and print a web address. This list appears in Settings → About.
- [ ] **Tests:** after a job, no files are left behind; after Clear history, every store is empty.

## Part 2: protecting ZPDF itself

**The honest limit:** the source is public on GitHub, and the release zip contains ZPDF's source, which the installer installs. Anyone can read it. Hiding Python or JavaScript code that ships as source isn't possible, and obfuscation only slows a determined reader down. What can be protected is the owner's **rights** and the **integrity** of what people install.

### Phase 4 (release D): rights

- [ ] **A copyright line in every source file** (`# Copyright (c) 2026 Tempura-446. Licensed under the PolyForm Internal Use License 1.0.0 with a personal-use permission; see LICENSE.`), plus a short header in the JavaScript, HTML and CSS. Add a test that fails if a new file lacks it.
- [ ] **The name and logo:** a `TRADEMARKS.md` saying the ZPDF name and icon may not be used for other software or modified copies. A trademark is protected by use; registering it is optional and costs money, so it's the owner's decision.
- [ ] **Copies on GitHub:** a short note in the README on reporting copies that break the licence (GitHub's DMCA process), and a `SECURITY.md` for reporting vulnerabilities privately.
- [ ] **Decision for the owner:** keep the repository public, or make it private again. Private hides the source on GitHub, but the release zip still contains it, and CI would go back to a limited allowance of minutes or the self-hosted runner. One middle way: keep the repository private and publish only built apps (the PyInstaller build) instead of the source zip. The installer would then install the built app. That hides plain source from casual readers, though the bundled Python can still be extracted.

### Phase 5 (release E): integrity of what friends install

- [ ] **Signed releases:** sign each release zip and its checksum with a key only the owner holds. A minisign or OpenSSH signature costs nothing; the public key is built into ZPDF. The Update button then refuses a zip whose signature doesn't verify, not just one whose checksum doesn't match, so a tampered release on GitHub can't install itself. `release.py` signs; the key lives on the owner's PC, never in the repository.
- [ ] **Code-signing the app (owner's decision, costs money):**
  - Authenticode-sign the launcher and the installer, through Azure Trusted Signing (about US$10 a month) or a code-signing certificate (about US$100–400 a year).
  - It removes the "Windows protected your PC" SmartScreen warning and proves the files came from the owner.
  - It works without it, but the warning stays.
- [ ] **Supply chain:**
  - pin dependency versions with hashes for the installer (`requirements.txt` with `--require-hashes`), so a hijacked package version can't be installed;
  - `pip-audit` in CI, weekly, for known vulnerabilities in dependencies;
  - GitHub's Dependabot alerts and secret scanning (free for public repositories);
  - CodeQL code scanning for Python and JavaScript.
- [ ] **The account:** two-factor authentication on the GitHub account, plus signed commits on `main`. The ruleset can require them once the owner's PC signs commits.
- [ ] **Tests:**
  - an update with a bad signature is refused;
  - a release made by `release.py` verifies with the built-in key;
  - the installer refuses a dependency whose hash doesn't match.

## Order and size

| Release | Phase | Size | Notes |
|---|---|---|---|
| A | 1: risk check on open, Make safe, safer links and attachments | medium | protects users the most, soonest |
| B | 2: certificate encryption, password strength, timestamp/LTV signatures, redaction proof | medium–large | |
| C | 3: temporary files, Clear history, no-telemetry list | small | |
| D | 4: copyright headers, trademark note, SECURITY.md, the public/private decision | small | mostly documents |
| E | 5: signed releases and updates, supply-chain checks, account hardening, optional code signing | medium | some steps need the owner (keys, 2FA, money) |

**Place in the roadmap:** D and the free parts of E (signed releases, `pip-audit`, Dependabot, secret scanning) are small and worth doing soon, right after 0.30. A comes next. B and C fit alongside the drawing tools, paragraph reflow and language packs.

**Decisions for the owner:**
- the repository public or private, and whether to publish built apps instead of the source zip;
- whether to pay for code signing;
- whether to register the ZPDF trademark;
- turning on 2FA and signed commits on the GitHub account.
